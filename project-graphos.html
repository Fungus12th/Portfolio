C (C99) FUSE3 Linux Kernel Graph Theory In Progress

GraphOS

A graph-native, project-oriented operating system that replaces traditional filesystem abstractions with a unified directed graph — where every entity (file, process, device) is a node and every relationship is an edge.

The Problem

Traditional operating systems handle files, processes, devices, sockets, and services through disconnected abstractions — hierarchical inode trees for files, process tables, socket descriptors, and separate service managers. These fragments don't talk to each other natively.

GraphOS asks: what if the OS itself was a graph? Every resource becomes a node, every relationship becomes a typed edge, and graph traversal replaces traditional lookup mechanisms entirely.

Architecture (6-Layer Design)

  • L0 — Linux Kernel (6.6 LTS): Base kernel providing hardware abstraction, scheduling, memory management, and device drivers.
  • L1 — GraphFS Core: The authoritative graph-native storage engine maintaining nodes, edges, content buffers, and traversal indexes.
  • L2 — Compatibility Shim: Bridges POSIX filesystem syscalls to graph mutations and queries via FUSE3, so standard tools (VS Code, Git, compilers) just work.
  • L3 — POS Runtime: Project lifecycle management with isolated namespaces, dependency resolution, and copy-on-write snapshots.
  • L4 — Intelligence Layer: Local inference for semantic code/file retrieval and predictive prefetch (planned).
  • L5 — Shell & UX: Visual graph navigator, graph shell (gsh), and system dashboard (planned).

The Graph Model

Everything in GraphOS is either a Node or an Edge:

  • Nodes: SYSTEM (root), DIRECTORY, FILE, PROCESS — with future types for DEVICE, SOCKET, SERVICE, and MEMORY.
  • Edges: CONTAINS (parent → child), USES (process → resource dependency), PARENT_OF (process hierarchy).

Paths like /projects/graphos/src/graph.c are resolved by tokenizing on / and traversing CONTAINS edges outward from the root node — no inode tables involved.

What Makes It Different

  • Graph-Authoritative Path Resolution: Directory lookup is a graph traversal, not an inode table scan.
  • Multi-Parent Hardlinking: A file node can have multiple CONTAINS edges from different directories — zero-copy, shared data buffer, no duplication.
  • Safe Edge Severing: Unlinking removes one edge. If other parents exist, the node survives. SEVER_ALL triggers cascading annihilation of all references.
  • Live Graph Introspection: Reading /.graph dumps the entire live in-memory graph topology. /.graph_cmd accepts graph-level directives as an IPC channel.

Development Roadmap

  • Phase 1 — Graph Core API: ✅ Complete. Standalone C library (libgraph.a) with node/edge CRUD, traversal, cascading deletion, and unit tests.
  • Phase 2 — GraphFS (FUSE3): ✅ Complete. ~513-line FUSE filesystem intercepting POSIX calls and mapping them to graph operations.
  • Phase 3 — Persistence: 🔄 Next. Serializing graph state to disk (nodes.dat, edges.dat).
  • Phase 4 — Extended CLI: 🔄 Partial. graphctl works with spawn, read, draw-edge, sever, and inspect commands.
  • Phase 5-6 — Process & Resource Graphs: 📋 Designed. Polling /proc to map running processes and file descriptors into the graph.
  • Phase 7-10 — Kernel Integration & Bootable OS: 📋 Long-term. Linux 6.6 fork-and-patch toward a bootable QEMU image.
